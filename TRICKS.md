# Engineering Tricks & High-Performance Optimization Patterns

This document details the architectural insights, database design philosophy, performance techniques, and domain patterns implemented in the **Alteva Web Crawler** system.

---

## 📐 Database Structure Insights & Design Philosophy

The database schema (`Jobs`, `Pages`, `JobPageLinks`, `JobStatusTransitions`) was designed around specific performance insights:

### 1. Indexed Persistent `url_crc32` Integer Column for $O(1)$ Deduplication
- **Insight**: Comparing `VARCHAR(2048)` strings on every link check causes heavy B-tree index traversal and disk I/O in MySQL.
- **Implementation**: The `Pages` table features `UrlCrc32` (`INT UNSIGNED`) with index `IX_Pages_UrlCrc32`. Lookups filter on the 32-bit CRC32 integer first before verifying exact URL string equality.
- **Generated by the database**: `UrlCrc32` is a persisted (`STORED`) generated column, `INT UNSIGNED AS (CRC32(NormalizedUrl))`, so the hash can never drift from the URL and every writer (API, scripts, other languages) gets it for free. EF maps it with `HasComputedColumnSql(..., stored: true)` and `DatabaseGenerated(Computed)`; the property has a private setter and code never assigns it. MySQL `CRC32` over utf8mb4 bytes matches C# `Crc32` over UTF-8 bytes (normalised URLs are percent-encoded ASCII), which a test verifies on a real MySQL server.
- **Upgrading old databases**: `EnsureCreated` never alters tables, so `SchemaUpgrader` (idempotent, checks `information_schema`) converts a legacy plain column at API start-up.
- **Not unique**: CRC32 collides, so the index is a lookup accelerator and the exact URL is always compared too. Idempotent upserts still need a collision-safe key.

### 2. Database Ground Truth + In-Memory Cache for Interruptible Crawling
- **Insight**: The database must remain the single source of truth so crawling jobs can be interrupted (paused/killed) and resumed at any time without data corruption.
- **Implementation**: a **per-job** in-memory `HashSet<uint>` of URL hashes suppresses duplicates before any HTTP request, while verified state is saved in MySQL. It is scoped to the job and discarded when the job ends (it is not an LRU and is bounded by the page limit). A single cache shared by all jobs was tried and caused a regression: a second crawl of the same site skipped every link and finished with one page.

### 3. Many-to-Many `JobPageLinks` Graph for Shared Page Disambiguation
- **Insight**: A single web page can be linked by multiple parent pages across different crawl jobs. A simple `ParentPageId` column on `Pages` would duplicate page content rows across jobs.
- **Implementation**:
  - `Pages` stores unique page metadata & content ONCE per normalized URL.
  - `JobPageLinks` records many-to-many directed graph edges (`JobId`, `SourcePageId`, `TargetPageId`).
  - Indexed foreign keys `IX_JobPageLinks_Job_Source` and `IX_JobPageLinks_Job_Target` allow instant sub-page tree retrieval.
  - **Index Disabling Note**: For ultra-high-throughput bulk link insertion, `IX_JobPageLinks_Job_Source` and `IX_JobPageLinks_Job_Target` non-clustered indexes can be temporarily disabled via `ALTER TABLE JobPageLinks DISABLE KEYS;` during mass ingestion and rebuilt afterward (`ENABLE KEYS;`).

### 4. Sequential Time-Ordered Job IDs (`SequentialGuid`, UUIDv7 layout)
- **Insight**: Random UUID v4 causes severe B-tree page splits and index fragmentation in MySQL InnoDB clustered indexes. Job ids are not secrets, so v4's unpredictability buys nothing here.
- **Implementation**: `SequentialGuid.NewSequentialGuid()` builds a UUIDv7-style value: 48-bit Unix-millisecond timestamp, a 12-bit per-millisecond sequence (rolls the clock forward after 4095 ids), version/variant bits and a random tail. It works on .NET 8, where `Guid.CreateVersion7()` does not exist. Timestamp and sequence are read under one lock so concurrent callers never share a pair (tested with 16,000 ids across 8 threads).

### 5. Single `CHAR(1)` Status Column & Status Transition Audit Table
- **Insight**: External SQL tools, non-typesafe scripts, and BI dashboards need simple status filtering without complex joins.
- **Implementation**:
  - `Jobs.status` uses a single `CHAR(1)` (`'P'`, `'R'`, `'C'`, `'F'`, `'X'`), mapped to C# `JobStatus` enum (`Pending`, `Running`, `Completed`, `Failed`, `Canceled`).
  - `JobStatusTransitions` table records full state transition history with timestamps and audit reasons.

### 6. On-the-Fly Domain Link Ratio & Indexed `domain_hash`
- **Insight**: Storing static domain link ratios on page rows creates stale data when new links are discovered.
- **Implementation**: Domain link ratios are calculated dynamically on the tree branches. `Pages` indexes `domain_hash` (`INT UNSIGNED`), enabling instant `COUNT(*)` domain matching queries.

## ⚡ Additional Performance Tricks

### 7. 64-Bit SimHash & Bitwise Hamming Distance Search
- Tokenizes page text into a 64-bit integer fingerprint (`SimHash`). Search queries are hashed into a 64-bit fingerprint and matched using bitwise XOR and Population Count (`BitOperations.PopCount(queryHash ^ pageHash)`).

### 8. Shared Pages & Real "Bytes Saved"
- A page is stored once per normalized URL in `Pages`; each job adds its own `JobPageLinks` rows pointing at it. The "bytes saved" metric is the **sum of the stored `ByteSize`** of pages that other jobs also reference (not an estimate).
- **Not implemented yet**: the worker still re-downloads a page another job already stored. True reuse needs the API to tell the worker which URLs are already stored; the worker has no DB access by design.

### 9. Stateless HMAC Session Token Verification
- Session tokens are cryptographically signed using HMAC-SHA256 (`Header.Payload.Signature`) and verified in memory by `AuthFilter.cs` without querying MySQL.

### 10. Twin Y-Axes 2D Progress Chart & Smooth Forecast
- Live progress is rendered on a 2D chart using two separate Y-axes (Left for page counts, Right for download bytes), with a smooth forecast continuation curve based on queue depth. History points use each page's real `ByteSize`, and the job shows average pages/s and KB/s.

### 11. Strict Page Limit with Slot Reservation
- Concurrent tasks reserve a slot with `Interlocked.Increment` before storing a page and give it back (`Decrement`) if the page is rejected or its file write fails, so the count can never overshoot `MaxPagesLimit`. Links are published for the last allowed page too, so its tree edges exist; nothing is queued once the limit is reached.

### 12. Failure Classification at the Source
- The worker sends one `PageCrawledEvent` shape for everything, and `IsSuccess` (2xx with content) decides what the API counts. Dead links, fetch errors, non-HTML and failed writes are stored on the page row but never inflate `TotalPagesCrawled` or bytes. The API also refuses to overwrite a page's stored SimHash/path/size with a later failed fetch.

### 13. Cancellation That Never Becomes a Broker Fault
- Each job owns a linked `CancellationTokenSource`. Cancellation exceptions are caught at every level and cleanup runs in `finally`, so MassTransit sees a normal completion and does not retry (and so restart) a canceled job. Final status events are published with `CancellationToken.None` so they survive cancellation, and "Completed" is skipped for canceled jobs. An unexpected error publishes `Failed` with a reason instead of leaving the job `Running`.

### 14. Text-Only Page Preview (XSS-Safe)
- The API extracts visible text with HtmlAgilityPack (script, style, comments removed) and the UI renders it in a `<pre>` as React text nodes; keyword highlighting splits the string into `<mark>` elements. Raw crawled HTML never reaches `dangerouslySetInnerHTML`.

### 15. Query-String-Safe, Traversal-Safe Storage Paths
- `StoragePathBuilder` maps `domain/path?query` to `domain/path_<sanitised>_<hash8>.txt`, so `?q=a` and `?q=b` never collide, and `IsUnderRoot` rejects anything resolving outside the root on read, write and delete. Behind `IStorageService` the same code path can later target S3.

### 16. Haxe/C# SimHash Parity
- The Haxe 64-bit SimHash uses the same algorithm as the C# `SimHashCalculator` (lower-cased `\w+` tokens hashed with CRC-64, per-bit voting), and a unit test asserts both produce the same fingerprint. See [HAXE.md](HAXE.md).

### 17. Classified, User-Visible Fetch Errors
- `CrawlErrorClassifier` walks the exception chain (`AuthenticationException`, `HttpRequestException.HttpRequestError`, `SocketException`, timeouts) and returns a `kind` plus a short message that travels on `PageCrawledEvent`, is stored on the page and rendered as badges. Because TLS failures are classified before any retry decision, the Polly policy skips them (no wasted back-off) while still retrying 5xx, 408, network errors and timeouts. A timeout caught only when the job token is not cancelled is the key distinction: otherwise `HttpClient`'s `TaskCanceledException` looks like a user cancel and the page silently disappears.

### 18. Job Status Is a Concurrency Token
- **Problem**: the API handles `PageCrawled` and the final `JobProgressUpdated` for one job at the same time. The first page's consumer loaded the job as `Pending`, then saved `Running` after the final event had already saved `Completed`/`Failed`, so finished jobs could stay `Running` forever (found by `EndToEndCrawlTests`).
- **Fix**: `Job.StatusChar` has `[ConcurrencyCheck]`. The page consumer saves the page first and the job update separately and drops its update on conflict; the progress consumer reloads and retries, so a terminal status always wins.
